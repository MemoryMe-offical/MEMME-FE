2. 업데이트 단계 설정
  src/hooks/useInAppUpdate.ts에서 22번 라인에

  updateType: IAUUpdateKind.FLEXIBLE,   // 유연 (현재 설정)
  updateType: IAUUpdateKind.IMMEDIATE,  // 즉시

  둘 중 하나로 설정

  FLEXIBLE (유연) — 현재 설정
    다운로드가 백그라운드에서 진행되고 앱을 계속 쓸 수 있음
    다운로드 완료 후 Alert로 재시작 유도
    일반적인 기능 업데이트에 적합

  IMMEDIATE (즉시)
    전체 화면을 덮는 업데이트 UI가 뜨고 완료 전까지 앱 사용 불가
    다운로드 완료되면 자동 재시작
    보안 패치, 서버 호환성 필수 업데이트에 적합
    onStatusUpdate 리스너와 Alert가 필요 없어짐 (자동이라서)

[Android 빌드 오류 총정리 - Gradle 9 + RN 0.83 환경]

① Gradle transform 캐시 손상 (metadata.bin 오류)
  원인: 이전 빌드 비정상 종료로 caches/9.0.0/transforms/ 내 파일 손상
  해결: 해당 transform 폴더를 \\?\ 긴 경로 접두사로 삭제 후 재빌드
  PowerShell: Remove-Item -LiteralPath "\\?\C:\Users\Owner\.gradle\caches\9.0.0\transforms\<hash>" -Recurse -Force

② Kotlin/Java JVM 타겟 불일치 (JDK 17 없는 환경)
  원인: Kotlin 2.1.x 기본값 JVM 21, Java 기본값 1.8 → 불일치
         react.internal.disableJavaVersionAlignment=true 가 없으면 RN이 JDK 17 툴체인 탐색 → 실패
  해결: android/gradle.properties에 두 속성 추가
    org.gradle.configuration-cache=false
    react.internal.disableJavaVersionAlignment=true   ← JDK 17 툴체인 탐색 방지
    kotlin.jvm.target.validation.mode=IGNORE          ← JVM 타겟 불일치 검증 무시

③ CMake 빌드 파일이 삭제된 transform 경로 참조
  원인: transform 폴더 삭제 후 node_modules 네이티브 모듈의 build/ 디렉토리가 이전 경로 참조
  해결: android/app/build, android/app/.cxx 및 영향받은 node_modules/*/android/build 삭제 후 재빌드

④ PackageList.java의 @react-native-firebase/app import 오류
  원인: 자동링킹이 io.invertase.firebase.ReactNativeFirebaseAppPackage 생성하지만
        실제 클래스는 io.invertase.firebase.app.ReactNativeFirebaseAppPackage
  해결: react-native.config.js에 dependencies 오버라이드 추가
    '@react-native-firebase/app': {
      platforms: { android: {
        packageImportPath: 'import io.invertase.firebase.app.ReactNativeFirebaseAppPackage;',
        packageInstance: 'new io.invertase.firebase.app.ReactNativeFirebaseAppPackage()',
      }}
    }

⑤ @react-native-firebase 패키지 dist/ 빌드 파일 누락 (Metro 번들 오류)
  원인: 패키지 설치는 됐으나 dist/module/index.js 등 빌드 결과물 없음
  해결: npm install --force @react-native-firebase/app @react-native-firebase/analytics
        → 24.1.1로 업데이트되며 해결됨

이 5가지를 각각 독립된 문제로 보고, 하나씩 해결하면서 합치는 식으로 접근하면 훨씬 덜 복잡해져요.

2. TypeScript 처음 쓸 때 꼭 알아야 할 것
TS는 “런타임 동작을 바꾸는 게 아니라, 컴파일 타임에 형검사만 추가된 JS”라고 생각하면 편해요.

이 프로젝트에서 먼저 쓸 TS 개념은 딱 3개만 잡고 시작해도 충분해요:

type / interface로 모델 정의

예:

ts
type MessageType = 'chat' | 'post';
interface ChatMessage { id: string; type: 'chat'; text: string; }
interface BoardPost { id: string; type: 'post'; title: string; content: string; }
type ChatBoardItem = ChatMessage | BoardPost; // 유니온 타입
목적: items 배열에 “chat인지 post인지”를 타입 레벨에서 강제.

컴포넌트 Props 타입

예:

ts
interface ChatMessageItemProps { item: ChatMessage; }
const ChatMessageItem: React.FC<ChatMessageItemProps> = ({ item }) => { ... };
목적: item에 .title 같은 필드 잘못 쓰면 컴파일 단계에서 잡게.

useState에 제네릭 타입 지정

예:

ts
const [items, setItems] = useState<ChatBoardItem[]>([]);
목적: setItems([...items, "문자열"]) 같은 실수를 미리 막기.
​

이 3가지를 이 화면에서 직접 써보는 게 TypeScript 입문이라고 생각하면 딱 좋아요.

3. 구현 순서 (진짜 작업 순서 느낌으로)
1단계: 데이터 모델만 먼저 설계
지금 코드 수정 안 하고, types/chatBoard.types.ts 하나 만들어서
ChatMessage, BoardPost, ChatBoardItem 타입만 우선 정의해봐.

이때 “롱프레스 후 게시판으로 변경”을 고려해서 구조를 설계하는 게 포인트:


리스트에는 두 종류의 아이템이 섞여 있음

채팅 메시지

게시판 글

둘 다 공통으로 가지는 정보

id: 고유 식별자

type: 'chat' or 'post'

createdAt: 생성 시각

채팅만 가지는 정보

text: 한 줄 메시지

isMe: 내가 쓴 메시지인지 여부 (지금은 항상 true지만 구조는 남김)

게시판만 가지는 정보

title: 제목 (채팅 → 게시판 변경 시, text가 여기로 옮겨짐)

content: 상세 내용

likes, commentsCount: 숫자들


공통 필드: id, type, createdAt

채팅에서 게시판으로 바꿀 때:

채팅의 text → 게시판의 title로 옮길 거지?

게시판의 content는 일단 빈 문자열 또는 기본 문구

이걸 미리 상상하면서 필드를 잡는 게 중요.

이 단계에서 질문:

“어떤 필드가 chat/post 모두에 필요하고, 어떤 필드는 타입별로만 필요한지?”
를 스스로 정의해보는 게 설계 연습이야.

목표: “채팅/게시글이 섞인 리스트” + “하단 입력창”만 먼저.

if (item.type === 'chat') { /* 채팅용 컴포넌트 */ }

이때 아이템 컴포넌트는 아주 심플하게 시작:

여기까지 되면 “TS 타입 + FlatList + 조건부 렌더링” 조합을 한 번 경험하게 됨.

3단계: 입력 영역 + 타입 토글 (채팅/게시판 작성 기능)
목표: 화면 아래에서

모드 버튼: “채팅 / 게시글” 토글

TextInput + 전송 버튼 → items 배열에 push

여기서 중요한 포인트:

messageType을 useState<'chat' | 'post'>('chat') 로 관리

handleSend에서:

if messageType === 'chat' 이면 ChatMessage 형태의 객체 생성

else 이면 BoardPost 형태의 객체 생성

둘 다 ChatBoardItem로 통합되는 구조

이 단계에서 TS가 도움 주는 지점:

newItem = { type: 'chat', ... } 를 만들 때, 빠진 필드가 있으면 빨간줄로 알려줌.

JS였다면 런타임에서야 알 실수를 이 단계에서 다 잡음.

4단계: onLongPress + 모달 동작만 먼저 붙이기 (내용 변경 X)

5단계: “채팅 → 게시판으로 변경” 알고리즘 생각해보기
이제 핵심 로직:

특정 id를 가진 ChatMessage를 찾아서,
그 자리에 BoardPost로 형태를 바꿔 끼우는 것.

순서를 머릿속으로 정리해보면:

selectedItem에 있는 ChatMessage 기준으로

setItems(prev => prev.map(item => { ... })) 사용

item.id === selectedItem.id 인 경우:

ChatMessage → BoardPost로 변환:

id, createdAt 그대로

type: 'post'

title: selectedItem.text

content: '' (또는 기본 텍스트)

likes: 0, commentsCount: 0

나머지 아이템은 그대로 반환

이때 TS는 item이 ChatBoardItem이기 때문에,

if (item.type === 'chat') 블록 안에서는 자동으로 ChatMessage로 좁혀주고

'post'로 새 객체를 만들면 BoardPost로 인식하게 돼.

실제 코드 짜기 전에, 이 알고리즘을 JS 느낌으로 먼저 써보고
그걸 나중에 TS로 옮기는 방식으로 가면 부담이 덜 함.
